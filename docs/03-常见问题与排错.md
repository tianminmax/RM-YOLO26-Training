# 常见问题与排错

这里的每一条都来自本次作业的真实记录，按「现象 → 原因 → 解决 → 证据」写。排错的通用顺序放在最后一节。

---

## A. 系统 / 资源类

### A1　训练把整机拖死，桌面完全无响应

**现象**：首次用默认参数（`workers=8`、`batch=16`、`imgsz=640`）启动冒烟测试，22 分钟连第 1 个 epoch 都没跑完，随后键鼠延迟超过 20 秒，只能强制重启。

**排查**：查上一次开机的 `/var/log/syslog`：

```
23:07:29 gdm-x-session: Keyboard: client bug: event processing lagging behind by 22883ms, your system is too slow
23:07:38 gdm-x-session: Touchpad: client bug: event processing lagging behind by 20794ms
23:09:13 kernel: sysrq: Emergency Sync complete     ← 按了 SysRq 紧急同步，说明内核还活着
```

**关键判据**：**没有任何 OOM-kill 记录，也没有 NVIDIA Xid 报错**。这说明不是显卡故障，而是整机资源耗尽后"缓慢窒息"——内核活着，但用户态已经调度不动。

**原因**：① dataloader `workers=8`，而机器有 32 线程，每个 worker 都会复制一份线程池，线程数爆炸式互相抢占；② 内存 14 GiB 且 **swap 为 0**，内存压力下无处换页，`systemd-oomd` 也报告 "Swap is currently not detected"，无法介入。

**解决**

```bash
# 1. 加 swap（只需一次）
sudo fallocate -l 6G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
# 2. workers 8 → 2
# 3. 训练脚本里在导入 torch 之前限制线程池
#    OMP_NUM_THREADS=4 / MKL_NUM_THREADS=4 / OPENBLAS_NUM_THREADS=4
```

**结果**：同样的数据从"22 分钟跑不完一个 epoch"变成"3 秒跑完一个 epoch"。

**经验**：训练时永远留一个终端跑 `watch -n2 'free -h | head -2; nvidia-smi --query-gpu=utilization.gpu,memory.used,temperature.gpu,power.draw --format=csv,noheader'`，`used` 超过可用内存的 85% 就立刻 Ctrl+C。

### A2　GPU 功耗被限制在 50W（性能只有一半）

**现象**：`nvidia-smi -q -d POWER` 显示 `Current Power Limit: 50W`、`Max Power Limit: 115W`。

**排查**：确认不是电池限电（`ADP0/online: 1`、电池满），并发现内核日志中有

```
NVRM: GPU0 ... failed to get platform power mode from SBIOS
```

——开源内核模块在部分笔记本（本次为 Legion）上读不到厂商功耗档位，退回保守值。

**解决**：`Fn+Q` 切到性能/野兽模式；`powerprofilesctl set performance`；必要时 `sudo nvidia-smi -pl 115`（重启后失效）。改功耗**只影响速度，不影响精度**，因此可以在训练中途调整而不污染对比实验。

---

## B. 显存 / 精度类

### B1　训练正常，但推理报 CUDA out of memory

**现象**：`imgsz=960` 训练时 batch=4 正常，但同一尺寸做推理（预标注）时 `batch=8` 直接 OOM。

**原因**：训练默认开启 **AMP（FP16）**，推理默认是 **FP32**，显存占用差近一倍；再加上 8G 卡的显示占用，剩余更少。

**解决**：① 把推理 `batch` 降到 2~4；② GPU 推理开启半精度（`half=True`）；③ 设 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 减少碎片。动态分辨率最大的 `imgsz` 也是显存杀手，必要时先降 imgsz 跑通流程。

**经验**：**"训练能跑"不代表"推理能跑"**，两者精度模式和峰值显存都不同，做批量推理前先小样本试跑。

---

### B2　AMP 到底有没有生效？

**容易误解的点**：配置里写了 `amp=True` 不等于实际用上了 AMP。ultralytics 在训练前会运行 `check_amp()` 自检——用一个小模型比对 FP16 与 FP32 的输出是否一致，**只有通过才真正启用**；若该显卡上 AMP 会引入异常，会打印 warning 并自动关闭（关闭后训练将以 FP32 进行）。

**怎么确认**：训练日志里搜 `AMP:`，出现 `AMP: checks passed ✅` 才是真在用；`checks skipped` 表示离线跳过；`checks failed` 表示被自动关闭。

---

### B3　CPU 推理太慢 / 进程被系统杀掉

**现象**：在没有 GPU 的环境里用 CPU 跑 300 张 `imgsz=960` 推理，进程被 SIGKILL（退出码 137）。

**原因**：CPU 推理的显存等价物是内存，批量列表过大 + 多线程会顶到系统上限。

**解决**：分块处理（每次 40~60 张，用 `--offset/--limit`），把 batch 降到 1；或直接换到 GPU 上跑（同样的活 GPU 只需几十秒）。

## C. 训练配置 / 流程类

### C1　续训之后曲线突然断裂（输入尺寸被静默改掉）

**现象**：中断后 `resume` 续训，单轮耗时从 23 秒骤降到 11.5 秒，验证 mAP50-95 从 0.6508 掉到 0.6022。

**原因**：ultralytics 的 `check_resume()` 允许续训时覆盖一批参数，其中包括 `imgsz`、`batch`、`workers`。启动脚本把默认的 `imgsz=640` 一并传入，覆盖了断点里的 960。

**为什么严重**：输入尺寸不是"快慢参数"，它决定模型学到的感受野与目标尺度，等于换了任务。

**解决**：在训练脚本中加入护栏——续训时读取断点中的 `imgsz`，与命令行不一致就直接报错退出：

```
拒绝执行：续训 --imgsz=640 与断点 imgsz=960 不一致。
改输入尺寸等于换任务，请用新的 --name 从头训练，不要在续训里改。
```

**经验**：续训只用 `last.pt` + `resume`，不要同时传任何会改变任务定义的参数。任何"曲线莫名其妙变了"的情况，第一步都去对比 `args.yaml` 与断点里的 `train_args`。

---

### C2　训练开始时提示 `Overriding model.yaml nc=80 with nc=1`

不是错误。这是把 COCO 的 80 类检测头替换为本题的 1 类，属迁移学习的标准动作，分类相关权重被重新初始化，backbone/neck 保留。

---

### C3　`~/.config/Ultralytics/settings.json` 写入失败

权限或只读文件系统导致的提示，不影响训练与结果。也可用 `YOLO_CONFIG_DIR=/tmp/ultralytics` 指定可写目录。

---

### C4　训练提前结束

正常行为。早停机制（`patience`）在连续多轮没有提升时自动停止；本次 baseline 在第 146 轮达到最优、196 轮停止，正是 patience=50 生效。提交时应使用 `best.pt`，而不是 `last.pt`。

---

### C5　GPU 利用率只有三四十，训练很慢

瓶颈在数据读取而非算力。此时**不要加 `--workers`**（会加剧内存压力，见 A1），正确做法是用 `--cache` 把解码后的图像缓存进内存（1057 张 640 尺寸约占 1.2G），或把数据集放到更快的磁盘。

---

## D. 数据类

### D1　把未标注图片当"背景负样本"直接加入训练

**为什么错**：这批图**大多数含目标**，配空标签等于告诉模型"这里什么都没有"，会直接压低召回率。

**正确做法**：要么人工标注，要么走"模型预标注 + 人工核对"的半监督路线。真正无目标的图片（如纯人群照）才可作负样本，且需人工确认。

---

### D2　图片与标签不成对

训练中途报错、或某些图被静默跳过。划分前应做一次配对检查（`prepare_data.py` 会检查并列出缺失项），确保每张图都有同名 txt。

---

### D3　标注规范不一致（本次实例：小地图区域）

**发现**：6855 个框中只有 108 个（1.6%）落在画面右下角的小地图区域，但小地图内的机器人图标明显更多——说明标注时对该区域"标一部分、漏一部分"。

**影响**：伪标注会产出大量"规范里没有"的小地图目标框；既可能带来额外召回，也可能变成误检。

**处理**：把这部分作为需要人工裁决的类别单独对待（`merge_addon.py --drop-minimap` 可一键过滤），并在文档里明确记录，而不是假装数据集是干净的。

---

### D4　用软链接组织数据集

`prepare_data.py` 用软链接而不是复制文件，省磁盘也便于回滚。注意：删除数据集目录时要小心，用 `rm -r` 删除软链接目录**不会**删除源文件，但用 `rm -rf` 直接指向被链接的真实目录会。

---

## E. 评估类

### E1　报告成绩时用了错的数据集

`val` 用于调参、`test` 只用于最终报告。一旦用 test 反复试参数，test 就退化成 val，成绩不再可信。本次 val 与 test 的 mAP50-95 仅差 0.0045，正是"划分干净 + test 只用一次"的结果。

### E2　同一个权重换尺寸评估，分数对不上

推理尺寸必须与训练尺寸一致（本次模型要用 `imgsz=960` 评估与推理）。分辨率不匹配会系统性地掉 0.02 左右，容易被误判为模型退化。

### E3　混淆矩阵的判定阈值

本仓库的混淆矩阵由 ultralytics 在 **conf=0.25、IoU=0.45** 下统计，与 `analyze_errors.py` 默认的 IoU=0.5 会有少量出入。做误差分析时需要先说明口径，否则数字对不上会被质疑。

## 通用排错顺序

遇到任何训练异常，按这个顺序走，比盲目改参数快得多：

1. **看日志找证据**：有没有 OOM-kill / Xid / traceback / 关键 warning。系统级问题先看 `syslog`/`journalctl`，不要一上来就怀疑显卡
2. **对比配置**：`args.yaml` 与断点 `train_args`、命令行参数是否一致。曲线变化异常时优先怀疑"配置被改"
3. **看资源曲线**：内存、显存、GPU 利用率、温度。决定是降 batch、加 cache 还是改 workers
4. **缩小规模**：`--fraction 0.02 --epochs 1 --imgsz 320` 跑一遍，能在 1 分钟内复现的问题都是链路问题
5. **换一个维度验证**：训练报错就用手动推理验证权重与数据；推理报错就用训练验证模型本身
6. **最后才调超参**：在链路与数据都干净之前，调参得到的结论都不可信
